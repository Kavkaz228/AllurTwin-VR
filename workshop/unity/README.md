# Нативное приложение VR Workshop для очков

Это Unity-проект для **HTC VIVE Pro 2 со штатными VIVE Controllers** и сетевым управлением серверным манипулятором. В этой PC VR-конфигурации Unity запускается на подключённом Windows-ПК: через SteamVR/OpenXR получает трекинг головы и контроллеров, отрисовывает сцену и интерфейс, передаёт цели движения. Шлем показывает изображение ПК. Сервер из корня репозитория выполняет обратную кинематику, проверку ограничений и столкновений, управление сеансами, запись траекторий и запросы к ИИ. Он может работать на том же ПК или на отдельной машине; у клиента нет собственного независимого симулятора робота.

**Проверено:** сцена «Цех» с AUTO прошла Editor Play Mode в Unity **6000.6.5f1**, включая управление обоими роботами и выпуск панели через оба поста; проверки видео на локальных тестовых источниках также прошли. Сервер прошёл **45/45** тестов Node.js. Точные результаты и ограничения — в `Logs/playmode-verification.json`. **14.10.2026 пользователь подтвердил кнопки и телепортацию в VIVE Pro 2**; журнал зафиксировал обе отслеживаемые руки и 26 выполненных переходов. Ведение робота физическим контроллером и реальная камера требуют отдельной проверки. После изменения кода или OpenXR-профилей необходимо пересобрать `Builds/Windows/VRWorkshop.exe`.

## Сборка, контроль качества и стоянка

Маршрут продолжается после покраски: на тот же кузов устанавливаются комплектующие, проводится учебный контроль сварки/покрытия/комплектности, готовая машина перевозится на одно из четырёх парковочных мест. Новая зона расположена за передним выходом покраски. Откройте «Выпуск» в карточке грузового конвейера и нажмите «Пуск участка» (после остановки сначала «Сброс»), затем запустите покраску, транспорт и сварку. Выбор автомобиля лучом показывает его паспорт.

Стоп, сброс и переподключение к тому же серверу сохраняют автомобили. Заполнение четырёх мест блокирует приём следующего кузова с покраски. Перезапуск самого сервера начинает новую симуляцию. Автомобили представлены собранными моделями; управление вождением и реальные измерения качества не реализованы.

## Быстрый запуск VIVE Pro 2

1. Установите VIVE Console и SteamVR через [мастер настройки HTC](https://www.vive.com/eu/support/vive-pro2/category_howto/setting-up-for-the-first-time.html). Подключите шлем, базовые станции и два контроллера, настройте игровую область. Проверьте их трекинг в SteamVR.
2. Назначьте **SteamVR активным OpenXR runtime** в его настройках. [HTC указывает SteamVR для VIVE Pro 2](https://service.viveport.com/hc/en-us/articles/4423262844813-How-to-setup-correct-OpenXR-runtime).
3. Запустите `Start-LocalWorkshop.cmd` из корня репозитория. Он поднимает сервер на `127.0.0.1:4180` и открывает `unity/Builds/Windows/VRWorkshop.exe`. На чистом ПК сначала нужны Node.js и `npm ci` в корне.
4. В приложении выберите `ws://127.0.0.1:4180/ws`, токен `local-training-only`, затем **Подключить**. Нажмите **ПОДКЛЮЧИТЬ** на нужном шкафу либо выберите робота и **Управлять** в панели. После остановки нажмите **Сброс** с отпущенным правым курком.
5. Удерживайте правый курок для ведения робота. Левый курок нажимает кнопки меню; нажатие левого трекпада запрашивает остановку. Сброс — отдельной кнопкой меню.

Только сервер: `powershell -NoProfile -File .\Start-LocalWorkshop.ps1 -ServerOnly` из корня. Журналы: `unity/Logs/player.log`, `local-server.log`, `local-server-error.log`. **Для VIVE Pro 2 Android Build Support, SDK/NDK и APK не требуются.**

Для запуска нового Windows-приложения с одноразовым подключением выполните из корня всего проекта:

```powershell
powershell -NoProfile -File .\Start-LocalWorkshop.ps1 -Connect
```

Уже открытый экземпляр сначала закройте. Адрес `ws://127.0.0.1:4180/ws` и локальный токен передаются через окружение запуска; токен не записывается в PlayerPrefs или файлы. Подключение начинает просмотр телеметрии без получения управления; фокус окна на мониторе для этого не нужен. Ключи `-Connect` и `-ServerOnly` несовместимы.

В настольном режиме просмотр телеметрии сохраняет соединение при потере фокуса. Если ручное управление или AUTO уже активно либо запрошено, потеря фокуса останавливает управление и отключает клиент. Полная приостановка приложения также отключает его. После отключения используйте **Подключить** в интерфейсе; для получения управления, выбора шкафа и запуска или сброса AUTO сначала вернитесь в окно приложения.

## Открытие проекта

1. На этой машине установлен **Unity 6000.6.5f1**; эта же версия указана в `ProjectSettings/ProjectVersion.txt`. На другом ПК установите её через Unity Hub и активируйте подходящую лицензию.
2. Для VIVE Pro 2 используйте целевую платформу Windows. Модули Android нужны только при отдельной сборке для автономной Android-гарнитуры.
3. В Hub выберите **Add project from disk** и именно эту папку `unity/`. Дождитесь восстановления пакетов из `Packages/manifest.json`.
4. Откройте сцену `Assets/VRWorkshop/Scenes/Цех.unity`. Для её создания используйте **VR Workshop → 1. Create workshop scene (Цех)**. Генератор создаёт геометрию цеха, сохраняет материалы в `Assets/VRWorkshop/Materials`, добавляет сцену в Build Settings, включает новый Input System и необходимые шейдеры. Повторный запуск генератора создаёт сцену заново: пользовательские изменения сцены предварительно сохраните отдельной копией. Если Unity попросит перезапуск редактора после смены Input Handling, выполните его.
5. Для первой проверки без очков достаточно нажать **Play**. Для гарнитуры выполните настройку OpenXR ниже.

Пол, стены, балки, свет, две рабочие ячейки, шкафы, столы, детали и площадки перехода **сохранены в сцене**: их видно и можно редактировать в Scene View до Play. Материалы также являются редактируемыми ассетами. `WorkshopClient` во время запуска добавляет камеру, контроллеры, визуализацию серверных роботов, панель и видеосистему, затем подключает действия к объектам сцены. Если сохранённой среды нет, предусмотрено создание той же геометрии при запуске.

Здесь нет зависимости от внешних моделей, Asset Store, Cinemachine или XR Interaction Toolkit. Применяются стандартный XR Feature API для поз и кнопок, Input System для мыши/клавиатуры, uGUI для панели; все модели собраны из встроенных примитивов.

Текущие версии из `Packages/manifest.json`: Input System **1.20.0**, OpenXR **1.18.0**, XR Management **4.7.0**, uGUI **2.6.0**.

## Проверка без гарнитуры

В терминале **корня репозитория**, а не `unity/`:

```powershell
npm ci
npm start
```

В сцене Unity нажмите Play, укажите:

| Поле | Значение для локальной проверки |
|---|---|
| Адрес сервера WebSocket | `ws://127.0.0.1:4180/ws` |
| Токен доступа | `local-training-only` |
| Оператор | произвольное имя оператора |

Нажмите **Подключить → Управлять → Сброс**. Отпустите все кнопки, затем удерживайте **Space** и двигайте тестовый контроллер:

| Клавиши | Действие |
|---|---|
| Space + W/A/S/D | Вперёд/влево/назад/вправо |
| Space + Q/E | Вниз/вверх |
| Space + стрелки | Наклон и поворот инструмента |
| Space + Z/C | Вращение вокруг третьей оси |
| G | Закрыть захват; отпускание открывает |
| Escape | Запросить остановку |

После STOP или отказа сервера нужен **Сброс**. Мышь работает с панелью в Game View. Потеря фокуса сохраняет соединение только при просмотре телеметрии; при активном или ожидающем ручном/AUTO-управлении сеанс прекращается. Для восстановления вернитесь в окно, нажмите **Подключить**, **Управлять** и при необходимости **Сброс**. Поле ввода или экранная клавиатура блокируют ведение инструмента.

### Обход и взаимодействие без очков

Без полученного права управления и без Space клавиши **WASD/QE** перемещают камеру, **Shift** ускоряет её, удержание **правой кнопки мыши** поворачивает обзор. Освободите управление роботом перед обходом цеха. Это камера осмотра; движение человека с физическими столкновениями не моделируется.

Щёлкните по двери, кнопке шкафа, выключателю света или площадке перехода. **F** также активирует объект под указателем. Для переноса детали подойдите на расстояние до 2,5 м, зажмите левую кнопку мыши и двигайте указатель; колесо меняет расстояние удержания. Отпускание возвращает детали физику падения.

**Tab** или **×** скрывает панель, освобождая весь экран для обзора. Кнопки **ПАНЕЛЬ** и **ПОДКЛЮЧИТЬ** шкафа открывают её снова. Ввод текста и настройка камеры блокируют перемещение инструмента.

## OpenXR для VIVE Pro 2 и Windows-сборка

Выполните **VR Workshop → 2. Configure Windows OpenXR**. Откройте **Project Settings → XR Plug-in Management**, выберите Windows/Standalone и проверьте, что включён OpenXR. В разделе OpenXR должен быть включён **HTC Vive Controller Profile** (`HTCViveControllerProfile`). Проверьте **Project Validation**. Подключите VIVE Pro 2, запустите VIVE Console и SteamVR; активный OpenXR runtime — SteamVR. Затем запустите Play с гарнитурой или выполните **VR Workshop → Build Windows player**. Выход: `Builds/Windows/VRWorkshop.exe`.

Штатный VIVE Controller использует цифровую боковую кнопку grip и нажимаемый трекпад. Назначения приведены ниже. Отдельный SteamVR Unity Plugin и платные плагины для текущего OpenXR-клиента не нужны.

### Если OpenXR или контроллеры не обнаружены

- **Изображение есть только на мониторе / runtime не найден:** запустите VIVE Console и SteamVR, убедитесь, что SteamVR отслеживает шлем; назначьте SteamVR активным OpenXR runtime и перезапустите приложение. В Editor дополнительно проверьте включение OpenXR для Windows.
- **Шлем работает, а кнопки не действуют:** убедитесь, что SteamVR видит оба контроллера и включён **HTC Vive Controller Profile**. После изменения профиля заново соберите Windows player.
- **Контроллер пропадает:** проверьте его заряд и видимость базовых станций в SteamVR. Клиент прекращает ведение при потере трекинга.
- **Не удаётся подключиться к роботу:** проверьте `http://127.0.0.1:4180/`, адрес WebSocket и токен. Отсутствие соединения с сервером и отсутствие OpenXR — разные состояния; подробности запуска записываются в `Logs/player.log` и серверные журналы.

## Необязательная сборка для автономного Android-устройства

**Автономная Android-гарнитура:** выполните **VR Workshop → 3. Configure Android OpenXR** и переключите Build Target на Android. Устанавливаются ARM64, IL2CPP, Vulkan, minimum API 29 и разрешение Internet. В настройках OpenXR включите группу поддержки конкретного устройства: для Quest — **Meta Quest Support** и профиль Touch. Запустите **Project Validation**, устраните ошибки и используйте **VR Workshop → Build Android APK**. Выход: `Builds/Android/VRWorkshop.apk`. Установите его обычным способом разработчика гарнитуры; например, при настроенном ADB: `adb install -r Builds/Android/VRWorkshop.apk`.

Этот вариант относится к другим автономным устройствам; на VIVE Pro 2 используется Windows EXE. Для Android через Unity Hub нужны **Android Build Support**, **Android SDK & NDK Tools**, **OpenJDK**. Android-сборка и совместимость её драйверов/устройства пока не проверены.

Основной режим использует два отслеживаемых контроллера. Если SteamVR передаёт только правый, интерфейс и перенос деталей доступны этой рукой; назначение руки видно в нижней подсказке. Оптическое отслеживание голых рук и тактильные перчатки не реализованы.

Официальные инструкции: [OpenXR 1.18: настройка проекта](https://docs.unity3d.com/Packages/com.unity.xr.openxr@1.18/manual/project-configuration.html), [OpenXR 1.18: ввод и профили](https://docs.unity3d.com/Packages/com.unity.xr.openxr@1.18/manual/input.html), [XR Management 4.7](https://docs.unity3d.com/Packages/com.unity.xr.management@4.7/manual/index.html).

## Подключение очков к серверу

Для VIVE Pro 2 сетевой клиент работает на Windows-ПК. Если сервер запущен на том же ПК, используйте `ws://127.0.0.1:4180/ws`. Для отдельного сервера нужен его DNS-адрес или IP, доступный с клиентского ПК, и WSS. Клиент не отключает проверку сертификатов. У автономной Android-гарнитуры `127.0.0.1` обозначает само устройство.

Пример настроек сервера в PowerShell; сертификат должен быть действительным для указанного имени и доверенным в Windows клиентского ПК (либо в ОС автономной гарнитуры):

```powershell
$env:HOST = '0.0.0.0'
$env:PORT = '4180'
$env:VR_ACCESS_TOKEN = '<собственный случайный ASCII-токен длиной не менее 24 символов>'
$env:TLS_CERT_FILE = 'C:\certs\robot-server-fullchain.pem'
$env:TLS_KEY_FILE = 'C:\certs\robot-server-key.pem'
npm start
```

В приложении: `wss://robot-server.example:4180/ws`, тот же токен, имя оператора. DNS-имя приведено как пример, его нужно заменить своим. Разрешите вход к выбранному порту из сети клиентского ПК. Для локальной разработки Windows на том же компьютере разрешён незашифрованный `ws://127.0.0.1:4180/ws`.

URI и имя оператора сохраняются в PlayerPrefs, **токен на диск не записывается**. После нового запуска его нужно ввести снова, если он не передан одноразовым запуском с `-Connect`. Внутри очков есть экранная клавиатура: строчные/прописные латинские буквы, цифры, символы URL и обычных ASCII-токенов, Очистить, Стереть и Готово. Для удобного ручного ввода используйте случайный hex-токен. Нажимайте клавиши лучом левого контроллера. На настольном клиенте работает обычная клавиатура.

## Управление в очках

Для взаимодействия нужна активная сессия OpenXR в шлеме: закройте панель SteamVR и вернитесь в цех. Фокус окна-зеркала на мониторе не определяет доступность VR-ввода. Кнопки читаются через Input System с привязками к HTC Vive Controller; луч выбора использует отдельную OpenXR aim pose. Нижняя подсказка показывает состояние трекинга, фокуса и счётчик полученных нажатий.

- **Левый курок** — выбрать кнопку, дверь, выключатель или площадку.
- **Левая боковая кнопка grip** — удерживать переносимую деталь в пределах 2,5 м; отпустить — положить.
- **Правый трекпад** — удерживать для дуги телепортации, отпустить для перехода к зелёному кольцу. Красная дуга/кольцо означает отказ. Стол, конвейер, занятые места и край пола проверяются физическими коллайдерами. Перед переходом освободите ручное управление и положите деталь.
- **Левый трекпад** — программный СТОП, назначение сохранено.

### Если приложение получает только правый контроллер

В этом режиме правый курок выбирает кнопки и объекты, боковая кнопка переносит деталь, а трекпад по-прежнему отвечает за переход. После получения ручного управления роботом правый курок **над панелью** нажимает её кнопки, а новый нажим **вне панели** разрешает вести робота. Нажатие, начавшееся на кнопке, не становится командой движения при отведении руки; сначала нужно полностью отпустить курок. Для работы с деталями и телепортации нажмите **Освободить**. СТОП на панели доступен правой рукой.

При появлении или исчезновении второй руки нужно отпустить курки и боковые кнопки. Незавершённый щелчок отменяется, переносимая деталь отпускается. В нижней подсказке отображаются получаемые роли L/R и причина блокировки перехода; подробности пишутся в `Logs/player.log`. Видимые модели контроллеров в панели SteamVR сами по себе не подтверждают, что обе роли поступают в приложение.

### Состояния операторского пульта

Пульт показывает следующий шаг: подключение, запрос управления, ожидание курка, ведение или сброс после остановки. «Ожидание команды» без `fault` не означает аварийную блокировку. «Освободить» доступно также во время запроса управления: задержанное разрешение сервера автоматически освобождается. AUTO не запускается, пока запрашивается ручной сеанс. При единственной правой руке панель с кнопками остановки и освобождения остаётся доступной во время ручного управления.

Манипуляторы имеют статическую начальную позу до подключения, с подписью «Учебная модель · нет телеметрии». При получении серверных данных показывается фактическая поза; при потере связи остаётся последняя поза с предупреждением. После запуска обзор один раз ориентируется на линию с учётом реального направления шлема.

Исправление проверено в Unity 6000.6.5f1: `Logs/xr-input-verification.json` — независимые кнопки рук, цифровой grip, правый трекпад, aim pose и потеря трекинга на синтетических VIVE-устройствах; `Logs/robot-visibility-verification.json` — обе полные модели до телеметрии и после обрыва; `Logs/interaction-verification.json` — реальные коллайдеры сохранённого цеха, дверь, перенос детали и допустимые места перехода; `Logs/panel-verification.json` — выбор кнопки лучом, перекрытие препятствием и отмена при потере фокуса; `Logs/focus-verification.json` — завершение сеанса управления. Все пять отчётов имеют `success: true`. Эти проверки не подтверждают нажатия физических контроллеров в шлеме; для повторного аппаратного испытания собран `Builds/Windows/VRWorkshop.exe`.

1. Левым контроллером укажите на панель, нажимайте левый trigger для выбора полей и кнопок. **Панель к себе** ставит панель перед текущим направлением взгляда. **Другой робот** циклически выбирает роботов из списка сервера.
2. Нажмите **Управлять**. Только один клиент владеет управлением выбранным роботом. После старой остановки нажмите **Сброс** с отпущенным правым trigger.
3. Нажмите и удерживайте **правый trigger**. В момент нажатия текущие положения руки и TCP становятся опорными. Движение руки смещает инструмент относительно этой опоры; поворот руки поворачивает инструмент по всем трём осям. Начальное нажатие не переносит инструмент в абсолютную позицию руки.
4. Отпустите trigger — движение прекращается. Можно удобно переставить руку и снова нажать trigger. Коэффициент смещения по умолчанию `0.6`, доступен в Inspector объекта WorkshopClient. Нажатие боковой кнопки **grip правого VIVE Controller** закрывает захват, отпускание открывает; кнопка цифровая.
5. **Нажатие трекпада левого VIVE Controller** или **СТОП** на панели запрашивает программную остановку. **Сброс** — отдельной кнопкой меню с отпущенным правым trigger. STOP на панели действует и для авторизованного наблюдателя. **Освободить** освобождает управление.
6. **Запись траектории** запускает запись на сервере; повторное нажатие её завершает. Файлы находятся в каталоге серверных записей и доступны через операторскую веб-панель.
7. Помощник отправляет текст и состояние робота на сервер. Источник **Ollama** обозначает ответ реально настроенной локальной модели; **Справочник** / `rules` — детерминированные подсказки при отсутствии модели или ошибке. Ни один вариант не отправляет команды движения. Переносимая установка модели описана в корневом README; из корня проекта используется `pwsh -File Setup-LocalAI.ps1`.

При потере трекинга, фокуса или свежей телеметрии клиент прекращает ведение. После обрыва сети соединение восстанавливается с задержкой; право управления и разрешение движения автоматически не возвращаются. Возраст телеметрии измеряется по монотонному времени **получения сетевого пакета**, а не по моменту его обработки кадром Unity.

### Шкафы, переходы и детали

- **Левый курок** активирует 3D-кнопки, открывает/закрывает двери шкафов, включает рабочие лампы и переносит оператора на отмеченные площадки. Луч учитывает препятствия и операторскую панель.
- **Левая боковая кнопка grip** берёт деталь с расстояния до **2,5 м**. Удерживайте её для переноса и отпустите, чтобы положить деталь. При потере трекинга предмет отпускается. Правая рука остаётся для ведения робота.
- **ПОДКЛЮЧИТЬ** шкафа выбирает соответствующего робота и запрашивает управление после получения его телеметрии. В учебной конфигурации шкаф 01 — `training-arm`, шкаф 02 — `training-arm-2`; сцена поддерживает два первых робота из списка сервера.
- **СТОП** шкафа адресуется его роботу, даже если в панели выбран другой. **СБРОС** требует управления этим роботом; **ОСВОБОДИТЬ** освобождает выбранный соответствующий сеанс.
- Подписка `watchAll` обновляет состояние обеих ячеек фактическими сообщениями сервера. При отсутствии свежих данных станция показывает потерю связи. Ручное владение отдельно для каждого робота; получение ручного сеанса останавливает всю автоматическую линию.

Перед переходом, работой с объектом или сменой шкафа клиент прекращает ведение инструмента. Движение снова разрешается только после отпускания правого курка и выполнения обычных проверок управления.

**Переносимые детали на столах — локальная физика Unity.** Захват деталей самим роботом не реализован. Серверная проверка пути использует собственные препятствия из конфигурации и не получает геометрию этих деталей, мебели и стен сцены. Перемещение предмета рукой оператора не изменяет серверную модель рабочего участка.

## Конвейер, AUTO и SCADA

Два учебных робота выполняют проход инструмента над металлическими панелями. Состояние конвейера, постоянные ID панелей, положение в метрах, стадии обоих постов и счётчик выпуска рассчитывает сервер. `ConveyorView` получает это состояние из телеметрии; собственного таймера выпуска панелей в Unity нет. Отображение замирает при потере свежих данных.

Конвейер направлен вдоль Unity +Z: начало `(0, 0.89, -2)`, длина 8 м; станции стоят на 2 и 6 м от начала. Центры панелей имеют Y = 0.95 м. Серверные локальные координаты робота преобразуются отражением Z; основания сцены — `(-1, .45, .2)` с yaw 0° и `(1, .45, 3.8)` с yaw 180°.

1. Подключитесь и освободите ручное управление обоими роботами.
2. В блоке SCADA **AUTO / КОНВЕЙЕР · СИМУЛЯЦИЯ** нажмите **Сброс**, затем **Пуск**, с отпущенным правым курком.
3. Наблюдайте стадии «подход → снижение → обработка → подъём → возврат» и фактическую скорость ленты. Во время обработки лента стоит.
4. **Стоп** в блоке AUTO останавливает оба робота и конвейер. Повторный пуск требует отдельного сброса. Сброс не обнуляет выпуск/панели и не двигает руки.
5. Получение ручного управления шкафом останавливает AUTO; перед ручным движением нужны обычный сброс робота, свежая телеметрия и удержание правого курка.

AUTO имеет отдельного владельца и heartbeat (250 мс, истечение 2 с). Отключение владельца, задержка серверного цикла более 300 мс и ошибки приводят к остановке с защёлкой. AUTO запрещён при настроенном физическом `rosbridge`-роботе. Переключение цех/SCADA не передаёт право управления.

Панели — кинематические Rigidbody, движущиеся по авторитетной позиции сервера; их нельзя забрать как свободный предмет. Это оригинальные процедурные металлические панели, не CAD автомобильного кузова. Роботы, текстуры и цех созданы для проекта без OEM-моделей и платных ассетов. Оптическая инспекция показана проходом TCP примерно в 65 мм над верхом изогнутого листа; тонкий визуальный лазер следует фактическому TCP только во время `process`. Распознавание дефектов, физика сварки, деформации, захвата роботизированным инструментом и синхронизация свободных предметов между клиентами отсутствуют.

Стрелки **‹ / ›** в шапке выбирают робота. Его кнопки находятся в отдельном блоке **Ручное управление**. **Значок перечёркнутого глаза** освобождает обзор цеха; **Вид целиком** доступен на ПК, **Панель к себе** — в VR. **Помощник ИИ** и **Камера** открывают соответствующие окна. Переключение представления не выдаёт сеанс и не запускает движение.

## Видео с камеры цеха или робота

По умолчанию настенный монитор показывает **виртуальную камеру** сцены. Это явно обозначенный обзор симуляции. Реальная камера не подключена; для её изображения нужно выбрать USB-устройство либо задать адрес своего сетевого источника.

1. Откройте **Настроить камеру** на операторской панели.
2. Кнопкой **Источник** выберите **USB-камера ПК**, **Сетевая камера · MJPEG** или **Сетевая камера · JPEG-снимки**.
3. Для сетевой камеры введите HTTP/HTTPS URL её MJPEG-потока или JPEG-снимка и нажмите **Применить адрес**. URL можно ввести экранной клавиатурой внутри очков. Изменение действует только до закрытия приложения.
4. **Переподключить** перезапускает выбранный источник. **Из файла** перечитывает постоянные настройки. На стенде монитора также есть 3D-кнопки смены источника и переподключения.

USB-камера запускается только после явного выбора этого источника. Нужны подключённое устройство и разрешение Windows на доступ приложения к камере. Если `deviceName` пуст, используется первое доступное устройство; для конкретной камеры укажите точное имя в настройках.

Для постоянных настроек измените `Assets/StreamingAssets/workshop-video.json` в проекте либо `VRWorkshop_Data/StreamingAssets/workshop-video.json` рядом с собранным EXE. Пример сетевого источника внутри массива `sources`:

```json
{
  "name": "Камера ячейки 01",
  "kind": "mjpeg",
  "url": "https://camera.example/stream.mjpg",
  "bearerTokenEnvironment": "WORKSHOP_CAMERA_TOKEN",
  "framesPerSecond": 15
}
```

Замените адрес адресом своей камеры. Для JPEG endpoint используйте `kind: "snapshot"`. Если авторизация не требуется, оставьте поля окружения пустыми. Для Bearer укажите **имя переменной окружения** в `bearerTokenEnvironment`; для HTTP Basic — имена в `usernameEnvironment` и `passwordEnvironment`. Значения задаются в среде запуска Unity/EXE, не в URL и не в JSON. Basic следует использовать с HTTPS. Клиент проверяет TLS-сертификат; автоматический шлюз или отключение проверки сертификата не предусмотрены.

**RTSP напрямую не поддерживается:** требуется отдельный шлюз RTSP → HTTP MJPEG/JPEG. Этот шлюз в проект не входит. CloudXR/WebRTC и удалённый рендеринг всей VR-сцены также не реализованы.

Монитор показывает источник, состояние и возраст кадра. Для сетевой камеры возраст — время с момента **полного получения кадра на клиентском ПК**, не задержка от момента съёмки. При переключении источника или ошибке старое изображение очищается; после превышения `staleAfterSeconds` изображение не выдаётся за свежий поток. Видео не является обратной связью для серверного разрешения движения.

## Что именно вычисляется на сервере

В штатном режиме Unity отправляет последнюю желаемую позу до 50 раз в секунду. Сервер присылает фактическую позу, звенья и состояние. Unity показывает полученные координаты звеньев и TCP; локальная обратная кинематика отсутствует. Для VIVE Pro 2 отрисовка, трекинг, физика учебных предметов и приём выбранного видеопотока выполняются на подключённом ПК, а изображение выводится в шлем. На автономном Android-устройстве клиентские задачи выполняются на гарнитуре; поддержка камер в такой сборке отдельно не проверена.

Объекты `Robot base 0` и `Robot base 1` в ячейках задают положение и ориентацию баз в комнате VR. Единицы — метры. Протокол использует правую систему координат, Unity — левую: позиция преобразуется `(x,y,z) → (x,y,-z)`, кватернион `(x,y,z,w) → (-x,-y,z,w)`. Преобразование поворота соответствует отражению базиса `R_unity = S · R_server · S`, а не простому отрицанию углов Эйлера.

Для симулятора показывается вся цепь звеньев из серверной телеметрии. Если физический адаптер передаёт только TCP и суставы без координат звеньев, Unity показывает TCP; для полной геометрии физической модели нужно добавить серверный расчёт звеньев по модели выбранного робота. Наличие подключения не подменяет подтверждение движения оборудования.

## AMAS/Cortex и Tecnomatix

Unity подключается **к серверу проекта**. В серверном слое подключаются AMAS/Cortex через подтверждённую схему сообщений поставщика, локальный роботный контроллер и отдельный шлюз проверки траекторий Siemens. Гарнитура не хранит пароли этих систем. Учебный манипулятор доступен сразу; реальные AMAS и Process Simulate требуют оборудования, установленного ПО и доступа поставщиков. Бесплатные клиентские пакеты Unity не предоставляют лицензии на эти продукты.

Интерфейс проверки Siemens и конфигурация физического адаптера описаны в документации сервера. Они не участвуют в непосредственном обновлении поворота головы или UI. Для физического участка дополнительно необходим локальный контроллер с проверенным watchdog/остановкой; кнопка в Unity является сетевым запросом остановки и не заменяет аппаратный E-stop.
